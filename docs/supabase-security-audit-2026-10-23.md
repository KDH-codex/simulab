# SimuLab Supabase 점검 — 2026-10-23

> 이 문서는 개편 전 위험과 최초 수정 상태를 보존한 기록이다. 이후 로컬 코드에서 관리자 인증·수집·랭킹 구조를 교체하고 SQL 004를 작성했다. 현재 구현과 테스트, 실제 DB 적용 순서는 [대규모 개편 적용 내역](overhaul-implementation-2026-10-23.md)을 확인한다. 운영 DB 적용 여부는 아직 확인하지 않았다.

## 결론과 확인 범위

Supabase를 방문 통계와 미니게임 랭킹에 사용하는 구성은 적절하다. 문제는 서비스 선택이 아니라 **관리자 권한을 브라우저에서만 검사하고, 공개 API가 입력 데이터를 지나치게 신뢰하는 방식**이다.

이 보고서는 저장소의 SQL 001~003, 관리자·랭킹·추적기 코드와 공개 화면을 검토했다. 운영 DB의 현재 정책·grant·함수 버전, 실제 유출 여부, 공격 이력, 비용은 확인하지 않았다. 방문자 원본 로그를 조회하거나 운영 랭킹에 테스트 데이터를 쓰지 않았다. 아래 문제는 저장소에서 확인한 위험이며, 운영 서버 적용 여부는 별도 확인해야 한다.

공개 브라우저 코드에 `anon` 키가 있는 것 자체는 정상이다. 이것은 서버 관리자 비밀키가 아니다. 보안 경계는 RLS, 함수 실행 권한, 서버의 인증·검증이다. `service_role`·secret 키는 브라우저나 공개 저장소에 두면 안 된다. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)

## 권장 데이터 흐름

관리자: `/admin` → Supabase Auth 로그인 → 유효한 사용자 JWT → 서버의 관리자 UID allowlist 확인 → 제한된 통계 RPC. 단순히 `authenticated`에 권한을 주는 것만으로는 모든 가입자가 관리자가 될 수 있으므로 부족하다. 브라우저에서 수정할 수 있는 user_metadata를 관리자 권한의 근거로 사용하지 않는다.

통계: 방문자 → 입력 허용목록을 가진 수집 endpoint → 길이·타입·빈도 검사 → 분석 테이블. 계산기에 입력한 소득·건강정보나 자유 입력을 event_label로 보내지 않는다. referrer는 필요한 경우 출처 호스트만 보관하도록 최소화하고, 전체 user_agent 보관의 필요성도 재검토한다. 최소한의 원시 로그 보관기간을 정하고 집계 결과와 분리한다.

랭킹: 게임 시작 시 서버의 일회성 세션 → 종료 시 게임 ID·점수·최소한의 검증자료 전송 → 속도 제한·중복 제출 방지·현실적인 범위 검사 → 서버가 시간·표시문자열 생성. 플레이 검증 없이 단순 상한만 두면 조작을 완전히 막을 수 없다. 당장 완전한 검증이 어렵다면 ‘사용자가 제출한 기록’임을 안내하고 상품·상금과 연결하지 않는다.

공개 리더보드는 의도된 공개 기능이다. 닉네임과 점수 공개 자체를 취약점으로 볼 필요는 없다. 다만 현재 테이블 전체 SELECT가 허용되므로 UI의 `limit=10`은 서버 접근 제한이 아니다. 공개할 열과 기록 범위를 결정하고, 닉네임에 실명·전화번호를 쓰지 않도록 안내한다.

## 운영 DB 확인 순서

1. 정확한 프로젝트의 SQL Editor에서 [읽기 전용 점검 SQL](../supabase/audits/read-only-security-check.sql)을 실행한다. 실제 방문자/랭킹 행과 비밀키를 읽지 않는다.
2. 함수 결과의 `anon_can_execute`, `security_definer`, `function_settings`를 확인한다. `anon_can_execute=true`이면 익명 실행 권한을 제거할 필요가 있다. auth 관련 단어가 있다고 안전한 것은 아니므로 함수 본문도 관리자 권한으로 검토한다.
3. Security Advisor 경고, RLS 정책, 뷰 옵션, table/column grants를 함께 확인한다. RLS가 켜졌다는 사실만으로 충분하지 않다.
4. 관리자로 사용할 Supabase Auth UID, 로그인 방식과 공개 가입 허용 여부를 결정한다. 확인된 관리자를 준비한 뒤 로그인 코드와 DB 권한을 함께 전환한다.
5. `PUBLIC`과 `anon`의 관리자 RPC EXECUTE를 철회한다. 일반 로그인 사용자에게도 관리자 검사 없이 응답하지 않도록 한다. SECURITY DEFINER가 꼭 필요하면 `SET search_path = ''`, 완전 수식된 테이블명, 관리자 확인, 1~90일 등 기간 제한을 적용한다.
6. 익명·일반 로그인·관리자 세 가지 권한으로 기대 응답을 검증한다. 공개 데이터는 공개되고, 일반 사용자는 분석 행/관리자 RPC를 볼 수 없어야 한다. 게임 등록·상위 기록·관리자 통계의 정상 동작도 확인한다.

익명 권한만 급하게 차단하면 현재 관리자 화면도 데이터를 읽지 못하게 된다. 응급으로 차단하는 경우에는 그 영향까지 알고 적용해야 한다. 본 작업은 운영 권한을 임의 변경하지 않았다.

## 개인정보·운영 확인 사항

확인된 전송 항목은 세션 ID, 도구 ID, 페이지 경로, referrer, user_agent, 방문 시각 및 이벤트 action/label/category다. 게임 등록은 닉네임, 게임 ID, 점수·표시값 등을 전송한다. 세션 ID는 무작위 문자열이라는 이유만으로 모든 법적 의미에서 익명 정보가 되는 것은 아니다. 호스팅/DB 사업자 자체의 접속 로그와 저장 지역도 별도 확인 대상이다.

운영 이메일은 사용자 답변상 **아직 없음**. 실제 연락처를 만들기 전 예시 주소를 공식 문의처로 안내해서는 안 된다. Supabase 프로젝트 지역, 계약 관계, 보관·파기 작업과 접근권한은 아직 확인되지 않았다. 그 값을 임의로 만들어 방침에 넣지 않는다.

| 확인할 항목 | 필요한 정보 |
|---|---|
| 서버 권한 | 읽기 전용 SQL 결과, Security Advisor 경고 이름 |
| 관리자 | Auth 사용 여부, 관리자 UID, 본인 확인 방식 |
| 데이터 수명 | 원시 방문기록/이벤트/랭킹 각각의 보관기간과 삭제 방법 |
| 국외 이전·위탁 | 프로젝트 지역, Supabase/Cloudflare/Google 실제 설정과 계약 관계 |
| 비용 | 현재 요금제, DB 크기, API 호출량·egress, 지출 알림 설정 |

## 공식 근거

- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security): 공개 API의 테이블 정책과 뷰 보안 확인 근거.
- [Supabase database functions](https://supabase.com/docs/guides/database/functions): SECURITY DEFINER, search_path 및 함수 실행 권한 관리 근거.
- [개인정보 보호법 제30조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029331583): 처리 목적, 보유 기간, 권리행사 등 방침 항목 검토 근거. 실제 의무 범위는 운영 형태와 처리 내역에 맞춰 검토해야 한다.

이 문서는 기술·운영 개선용 진단이며 법률 적합성이나 침해사고 부재를 보증하는 문서가 아니다.

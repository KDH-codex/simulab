# 대규모 개편 적용 내역 — 2026-10-23

## 적용 상태

로컬 소스와 `dist` 공개 빌드에 적용했고 운영자가 전체 배포를 요청했다. GitHub main → Cloudflare Workers Builds 자동 배포 연결을 확인했다. 실서비스 반영 결과는 배포 완료 보고를 기준으로 확인한다. 운영 Supabase SQL 적용과 관리자 UID·운영 이메일 설정은 프런트엔드 배포와 별개이며, 아래 전환 절차가 필요하다.

운영자 요청으로 Supabase 연결·운영 SQL 적용·관리자 계정 등록은 후순위로 보류한다. 이번 배포에서는 홈·공개 도구·정책 페이지와 서버 권한 확인이 필요한 새 관리자 로그인 화면을 반영한다. 선택 통계·원격 랭킹·광고 자동 로드는 비활성 상태를 유지한다.

사용자가 제공한 프로젝트 목록 화면에서 `simulab`, Free 플랜, 지역 `ap-south-1`을 확인했다. 이 지역은 Supabase 문서상 뭄바이에 해당한다. 연결된 프로젝트 URL과 세부 위탁·보관 설정은 별도로 확인해야 한다. [Supabase 지역 안내](https://supabase.com/docs/guides/platform/regions)

## 재현 가능한 실행

```powershell
npm ci
npm test
npm run build
node scripts/check-public.mjs
npm run preview
```

미리보기: `http://127.0.0.1:4180/`. 운영 DB 요청을 로컬 오류 응답으로 전환하므로 실제 데이터를 쓰지 않는다. 미리보기에서 실제 관리자 비밀번호를 입력할 필요가 없다. 모바일 확인용: `/__mobile?width=360&path=/`.

테스트는 행사, 입력·출력 보안, 관리자 인증, 세션 지표, 대표 계산 사례를 다룬다. 개발용 PGlite PostgreSQL 엔진에서 기존 SQL 001~003과 새 004를 실제 실행해 익명·일반 계정·관리자 권한, 원시 INSERT 거부, 값 검증과 중복 제한을 확인한다. 이것은 운영 DB의 설정·데이터나 Supabase Auth 서비스 전체를 검증한 것은 아니다. 51개 도구의 모든 수식을 인증하는 것도 아니다.

최종 자동 검증: `npm test` **33개 통과**, 공개 HTML **59개**의 내부 자산·canonical·확대 설정·내부 자료 제외 검사 통과, `git diff --check` 통과. 공개 빌드는 **202개 파일**, 사이트맵 **56개 URL**이다. 관리자와 네이버 소유권 확인 HTML은 사이트맵에 포함하지 않는다.

브라우저에서 홈 검색·빈 결과·개인정보 설정, 360px 모바일 레이아웃과 메뉴, 행사 카드의 실제 운영일 링크, 평수 환산, 이름 검색·찜, 게임 4개의 기기 저장 안내와 관리자 로그인 실패 시 차단을 확인했다. 평단가 입력을 바꿨을 때 회차별 금액이 갱신되지 않던 표시와 상승한 평균단가를 ‘인하’라고 표현하던 문구도 수정했다. `100원×10주 + 200원×10주`는 회차별 1,000원/2,000원, 합계 3,000원, 평균 150원, +50% 변동으로 확인했다.

## 운영 Supabase 전환 순서

1. 연결 프로젝트가 `assets/js/supabase-config.js`의 Project URL과 일치하는지 확인한다. 공개 anon 키를 service_role 비밀키로 바꾸지 않는다.
2. Supabase 프로젝트의 **Authentication → Users**에서 관리자용 앱 계정을 준비한다. 운영자가 Users 목록이 비어 있다고 확인했으므로 앱 계정부터 생성해야 한다. **Add user → Create new user**에서 운영자가 소유한 이메일과 별도 비밀번호를 직접 입력한다. 본인 소유 이메일을 확인한 경우에만 해당 사용자 생성 창의 Auto Confirm User 옵션을 사용할 수 있다. 프로젝트 전체의 이메일 확인 설정을 끌 필요는 없다. 생성한 사용자의 UID를 확인한다. Supabase 대시보드에 로그인한 계정과 앱 Auth 계정은 별개다. 비밀번호와 비밀 API 키는 공유하지 않는다. 계정 생성만으로 관리자 권한이 부여되는 것은 아니며, 아래 004 적용과 allowlist 등록이 필요하다.
3. [읽기 전용 점검 SQL](../supabase/audits/read-only-security-check.sql)로 실제 함수·정책·grant를 확인한다.
4. 기존 테이블이 있는 프로젝트에는 [004 보안 migration](../supabase/migrations/004_harden_admin_and_public_writes.sql)만 검토·적용한다. 001~003의 정책을 무조건 다시 생성하면 중복 오류가 날 수 있다. 004는 기존 기록을 삭제하지 않는다.
5. SQL Editor에서 아래 `관리자_UID`를 Authentication 사용자의 실제 UUID로 바꿔 등록한다. 로그인 이메일이나 프로젝트 ID를 넣는 칸이 아니다.

```sql
INSERT INTO simulab_private.admin_users(user_id)
VALUES ('관리자_UID'::uuid)
ON CONFLICT (user_id) DO NOTHING;
```

6. 새 관리자 화면에서 운영자가 로그인해 통계 조회를 확인한다. 일반 계정과 익명 접근은 거부되어야 한다. 새 RPC가 없거나 관리자 목록이 비어 있으면 대시보드는 열리지 않는다. 기존 관리자 화면은 새 SQL과 호환되지 않으므로 프런트엔드와 함께 전환한다.
7. 운영 이메일·기존 로그 보관 및 파기·원격 랭킹 보관기간과 삭제 요청 절차·처리 지역 등 실제 운영 내용을 확정한다. 방침 생성 원본 `scripts/build-legal.mjs`와 `assets/js/site-settings.js`를 실제 설정에 맞춰 수정한다.
8. 확인을 마치면 `analyticsEnabled`, `rankingRemoteEnabled`를 각각 활성화할 수 있다. 통계는 이용자가 허용한 경우에만 수집한다. 광고는 승인과 해당 지역의 동의 요구사항 및 실제 스크립트 배치가 준비된 뒤 별도로 통합한다.

선택 통계는 전용 수집 RPC가 전체 분당 120건, 점수 등록은 전체 분당 60건과 같은 기기 식별자 30초 간격으로 제한한다. 이 수치는 초기 소규모 운영용 제한이다. 식별자는 사용자가 바꿀 수 있으므로 사용자별 부정행위의 완전한 방어가 아니며, 트래픽이 늘면 서버 앞단의 추가 제한과 검증이 필요하다. 실제 플레이 검증은 아직 구현하지 않았다.

보관 목표 30일은 기존 운영 DB에 자동 삭제 작업이 적용됐다는 뜻이 아니다. 실제 보관·파기 정책과 작업을 확인하기 전 신규 분석 전송은 기본 보류 상태를 유지한다.

## Cloudflare 배포

Workers Static Assets는 저장소의 wrangler.json에 `build.command`와 `assets.directory=./dist`를 설정했다. Pages Git 빌드라면 계정에서 빌드 명령 `npm run build`, 출력 폴더 `dist`를 지정해야 한다. 어느 방식을 쓰는지는 아직 계정 설정을 확인하지 못했다.

루트 폴더 전체를 정적 파일로 업로드하지 않는다. 배포 후 홈, 행사·대표 계산기·게임, 관리자 로그인, 개인정보 설정을 확인하고 `/docs/`, `/supabase/`, `/tests/`가 공개 자산에 포함되지 않는지 확인한다. 소유권 메타/ads.txt는 Google이 지원하는 확인 방식이지만 승인 결과를 보장하지 않는다. [AdSense 사이트 연결 안내](https://support.google.com/adsense/answer/7584263?hl=en)

- Cloudflare Workers/Pages 실제 배포 설정과 AdSense 승인 상태 변경: 계정에서 확인 필요.

## 우선 보완할 사항

### 1. 자동 수집과 사실 검증 실행 경로를 구체화해야 한다

`scripts/collect-event-candidates.mjs`는 후보를 `scratch`에 저장한다. `scripts/events/candidates.mjs`도 검증 상태를 `pending`으로 남기며 확인일·무료 여부·어린이 자격을 만들어 넣지 않는다. 이것은 재사용할 수 있는 정상적인 후보 수집 기반이지만 자동 공개 경로는 아니다.

로컬 프로세스의 TourAPI 키는 설정되지 않았고 `.env.local`도 없다. 다른 실행환경의 비밀 설정 유무는 확인하지 않았다. 세일에는 검토 원본과 생성기는 있지만 공식몰별 자동 수집기가 없다. 신규 7개 항목의 공급자 URL도 실제 상세 레코드를 수집한 실적으로 간주할 수 없다.

진행 조건은 공급자마다 수집 방식, 상세 근거 필드, 자동 검증 허용 기준, 검토가 필요한 예외, 실패 상태를 먼저 정의하는 것이다. 키가 필요한 출처는 인증 상태를 별도로 보고하고 공개 HTML 등 가능한 경로를 검토한다.

### 2. 현재 로컬 예약과 PC 없이 실행되는 작업을 구분해야 한다

확인된 로컬 Codex 예약은 `나들이·브랜드 세일 달력 정기 검토` 1개다. `ACTIVE`인 heartbeat이며 월·목 오전 9시 규칙으로 축제와 세일을 함께 검토한다. 로컬 저장 상태의 `last_run_at`은 비어 있고 실행 이력은 0건이다. 다음 실행은 2026-10-26 08:57:42 KST로 기록되어 있다. 이 기록은 예약 설정의 증거이며 수집·배포 성공 증거가 아니다.

9개 수집 슬롯과 수·목 블로그 큐는 현재 로컬 예약에서 확인되지 않았다. 문서에서 언급한 화요일 세일·목요일 축제 블로그의 기존 예약도 이 로컬 자동화 목록에서 발견되지 않았다. 다른 서비스나 계정에 존재하는지까지 확인한 것은 아니다.

OpenAI 공식 문서도 로컬 프로젝트 예약에 컴퓨터와 앱이 실행 중이어야 한다고 설명한다. PC 없이 사이트를 갱신하려면 서버 실행환경과 그 환경에서 가능한 검증 단계가 필요하다. 로컬 예약에 설정한 권한·로그인·브라우저 세션이 서버로 자동 이전된다고 가정하면 안 된다.

- 공식 문서: <https://learn.chatgpt.com/docs/automations?surface=app>
- 현재 예약의 명목 시각과 실제 다음 실행 시각도 다르므로 08·15·19시는 기본 시간대로 다루고 정각 완료를 약속하지 않는다.
- 문서의 `timing_mode=flexible_schedule`·`default_timezone`는 요구 의도다. 현재 노출된 예약 도구의 명시적 입력 필드에는 없으므로 사용 가능한 스케줄러 설정으로 변환·검증해야 한다.
- 새 경로를 검증한 후 기존 예약 1개의 축제·세일 부분을 함께 대체한다. 그 전에 기존 예약을 끄거나 9개 작업을 중복 활성화하지 않는다.

### 3. 블로그 분야 분리가 최신 세일 분류를 빠뜨린다

첨부 1절의 세일 분리안은 라이프·패션·유아/키즈·가구의 4개다. 현재 `tools/parenting-deals/model.js`의 실제 분류는 라이프·패션·뷰티·유아/키즈 패션·가구/리빙·가전/디지털·주방용품의 7개다. 현재 공개 데이터에도 뷰티 세일이 있다.

블로그 분리 기준은 기존 `CATEGORIES`의 전체 제외 분류를 재사용하는 것이 적절하다. 현재 4개만 고정하면 뷰티가 누락되고 나머지 추적 분야의 향후 세일도 빠질 수 있다. 유효 항목이 있는 분야만 글을 만들고, 상시 회원·앱 혜택은 기존 원칙에 따라 대표 세일과 구분한다.

### 4. 네이버 발행 경로와 결과 불명 상태를 설계해야 한다

이 저장소에는 블로그 원고 생성기, 수·목 큐, 발행 이력 저장소가 없다. 이번 검토에서 네이버 로그인·편집기·기존 승인 범위도 검증하지 않았다. 원고·캡처 자동 준비와 실제 게시까지의 연결을 각각 시험해야 한다.

문서의 주차·항목·지역/분야 기반 중복 키는 적절하다. 여기에 `prepared / publishing / published / failed / unknown / held` 같은 상태를 더하는 것이 필요하다. 게시 버튼 이후 응답을 받지 못한 경우에는 이미 게시됐을 수 있으므로, `unknown`으로 두고 실제 게시 URL을 대조한 뒤 재시도해야 한다. 단순히 실패로 분류해 재게시하면 중복 글이 생길 수 있다.

기존 일괄 승인 범위가 확인되면 배치 단위로 적용한다. 이번 검토 요청을 실제 블로그 게시 승인으로 해석하지 않았다.

### 5. 확인시각·내용 버전·배포 성공을 분리해야 한다

내용이 그대로여도 공식 원문을 실제 재검증했다면 재검증 성공 기록은 남아야 한다. 반면 빌드나 실행만 한 경우 `verifiedAt`을 갱신하면 안 된다. 문서의 '변경이 없으면 확인시각을 무의미하게 다시 쓰지 않는다'는 문구는 이 둘을 구분하도록 구체화한다.

- `contentHash`·내용 revision: 실질 내용 변경 기준.
- 실제 확인시각·공급자 마지막 성공: 실제 원문 재검증 기준.
- 빌드 시각: 생성 시각이며 확인일이 아님.
- 배포 영수증: 커밋, 스냅샷, 운영 URL의 일치 확인 결과.

기존 `checkedAt`의 날짜 정밀도는 보존하고 과거 시각을 새로 만들어 넣지 않는다. 한 항목을 갱신할 때 다른 항목의 정상 원본·검증시각·공급자 실패 상태를 유지한다. 동일 레코드가 여러 분류에 속할 때도 분류별 누락을 취소/삭제로 오인하지 않아야 한다.

## 권장 진행 순서

1. 9항목·9슬롯·수목 분리 정책의 단일 구성과 공통 데이터 계약을 구현한다. 최신 7개 세일 분류와 기존 7개 지역 권역을 재사용한다.
2. 기존 축제·세일 어댑터와 신규 7개 항목의 실제 출처별 수집·검증 경로를 구현한다. 인증 필요·차단·공고 0건·일부 실패를 구분한다. 항목 하나로 구조를 먼저 검증하더라도 최종 범위는 9개 전체다.
3. 공개 원본·허브·allowlist 피드·항목별 revision·실행 이력을 연결한다. 각 항목의 실제 공식 레코드로 수집부터 공개물까지 시험한다.

5. 공개 피드 기반 원고·캡처·발행 전 재검증·안정적인 발행 키·결과 불명 처리를 구현하고 네이버 발행 경로를 검증한다. 그 후 수·목 큐를 활성화한다.
